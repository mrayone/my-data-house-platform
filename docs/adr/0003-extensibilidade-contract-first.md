# ADR-0003 — Tornar a plataforma extensível por contratos declarativos com codegen

- **Status:** Accepted
- **Data:** 2026-09-13
- **Decisores:** Engenharia de Software, Engenharia de Dados
- **ADRs relacionados:** 0002, 0006, 0007, 0009

## Contexto

O cenário real tem **~30 tópicos** e crescerá. Cada tópico, no desenho
tradicional, exige seis artefatos coerentes entre si: schema Avro, tópico Kafka,
tabela de landing, config de connector, MV de landing→core e tabela core. Seis
lugares para errar, por tópico, sem nada que garanta que continuam consistentes.

O requisito explícito do projeto é *"arquitetura extensível para plugar mais
tópicos e gerar views"*. Extensível aqui significa **custo marginal quase
constante** e **impossibilidade estrutural de inconsistência** — não "é fácil
copiar e colar".

## Decisão

Existe **um único artefato editado à mão por entidade**: o **descritor de
contrato** em `contracts/domains/<contexto>/<entidade>.yaml`, validado por
`contracts/schema.json`.

Do contrato, `dhctl generate` **gera**:

| Saída | Destino | Editável à mão? |
|---|---|---|
| Schema Avro do valor e da chave | `schemas/avro/<ctx>/<entidade>-{value,key}.avsc` | **Não** |
| DDL da tabela de landing (L0) | `internal/contexts/<ctx>/sql/10-landing/<seq>__<entidade>_raw.sql` | **Não** |
| Config do connector | `deploy/connect/connectors/<topic>.json` | **Não** |
| Definição do tópico Kafka | `deploy/kafka/topics.yaml` (entrada) | **Não** |
| Esqueleto da MV L0→L1 e da tabela core | `internal/contexts/<ctx>/sql/20-core/<seq>__<entidade>.sql.tmpl` | **Sim, é esqueleto** |

Todo arquivo gerado começa com:

```
-- GENERATED by dhctl from contracts/domains/<ctx>/<entidade>.yaml — DO NOT EDIT
-- contract-hash: <sha256 dos 12 primeiros chars>
```

`make verify` roda `dhctl generate --check`, que **falha se qualquer arquivo
gerado divergir do contrato**. Isso torna a inconsistência um erro de build, não
um bug de produção.

### Anatomia do descritor

```yaml
apiVersion: datahouse/v1
kind: EntityContract
metadata:
  context: sales
  entity: order
  owner: time-ecommerce
  description: Cabeçalho do pedido replicado do SAP via Datasphere
source:
  system: sap
  cdc: datasphere
  topic: sap.sales.order.v1
  partitions: 6
  key: [order_id]
  # coluna monotônica que ordena versões da mesma chave
  version_column: cdc_seq
  operation_column: op          # c | u | d | r
  soft_delete_operations: [d]
schema:
  fields:
    - name: order_id      type: string     nullable: false  doc: PK do pedido no SAP
    - name: customer_id   type: string     nullable: false
    - name: business_unit_code type: string nullable: false
    - name: order_status  type: string     nullable: false
    - name: currency      type: string     nullable: false
    - name: total_amount  type: decimal    precision: 18  scale: 4
    - name: created_at    type: timestamp_micros
    - name: updated_at    type: timestamp_micros
landing:
  partition_by: toYYYYMM(_kafka_ts)
  order_by: [order_id, _cdc_seq]
  ttl_days: 180
core:
  engine: ReplacingMergeTree
  order_by: [order_id]
  partition_by: toYYYYMM(created_at)
  # relações declaradas: alimentam docs e validação, não geram JOIN automático
relations:
  - to: customer/customer
    kind: foreign_key
    join_on: { local: customer_id, remote: customer_id }
  - to: organization/business_unit
    kind: lookup
    join_on: { local: business_unit_code, remote: bu_code }
extensions:
  serving: true        # exposto pela API
  analytics: true      # participa de marts
```

**`relations` é documentação executável**: não gera join. Serve para (a) desenhar
o mapa em `docs/architecture/data-flow.md`, (b) validar que uma relação declarada
aponta para um contrato existente, (c) gerar os checks de integridade
referencial do ADR-0010. A decisão de *como* correlacionar é sempre humana e vive
no ADR-0005.

### Tipos suportados no contrato

`string`, `bool`, `int32`, `int64`, `float64`, `decimal(p,s)`, `date`,
`timestamp_millis`, `timestamp_micros`, `bytes`, `array<T>`, `map<string,T>`,
`enum`. Cada um tem mapeamento fixo Avro↔ClickHouse na tabela de
`docs/architecture/extensibility.md`. **Tipo novo exige alterar o gerador e
documentar o mapeamento** — nunca improvisar no YAML.

## Alternativas consideradas

### A) Escrever os seis artefatos à mão por tópico
- **Prós:** zero infraestrutura de codegen; controle total caso a caso.
- **Contras:** 30 tópicos × 6 artefatos = 180 arquivos sem garantia de coerência;
  divergência é inevitável e silenciosa.
- **Por que não:** o requisito de extensibilidade é o núcleo do projeto.

### B) Derivar tudo do Schema Registry (schema como fonte da verdade)
- **Prós:** uma fonte só, já existente; nada duplicado.
- **Contras:** o Avro do SAP não carrega as decisões que precisamos —
  `ORDER BY` do ClickHouse, TTL, chave de dedup, coluna de versão, partição,
  quais relações existem, se a entidade é aplicacional ou analítica. Essas
  decisões são nossas, não do SAP.
- **Por que não:** o schema descreve o payload; o contrato descreve o payload
  **mais** as decisões de plataforma. Precisamos dos dois — o contrato gera o
  schema, e no cenário real (schema já existente no SAP) o `dhctl contract
  import --from-subject` gera o rascunho do contrato a partir do subject e o
  humano completa as decisões.

### C) Geração em tempo de execução (a aplicação lê o contrato e cria DDL)
- **Prós:** nada versionado; sempre "atual".
- **Contras:** DDL invisível em code review; impossível saber o estado do banco
  a partir do repositório; rollback não existe.
- **Por que não:** conflita com ADR-0007 (migrations versionadas e revisáveis).

## Consequências

### Positivas
- Plugar tópico: 1 YAML + `make generate` + `make bootstrap`. Nenhum Go novo.
- Inconsistência entre schema, DDL e connector torna-se erro de CI.
- O contrato é o documento que o time de dados e o de aplicação leem juntos.
- O mapa de relações do domínio nasce dos contratos e não apodrece.

### Negativas / custo aceito
- Precisamos construir e manter o gerador (Fase 02). É o investimento que paga
  os 30 tópicos.
- Uma indireção a mais: quem procura o DDL acha um arquivo gerado e precisa saber
  ir ao contrato. Mitigado pelo header obrigatório e pela tabela do §3 do
  `CLAUDE.md` raiz.
- Tipo exótico do SAP pode não caber no vocabulário de tipos. Mitigação: falhar
  alto na validação com mensagem apontando o tipo, nunca degradar para `String`
  silenciosamente.

## Impacto no repositório

- `contracts/schema.json`, `contracts/domains/**`, `contracts/CLAUDE.md`
- `internal/contract/` (parse + validação), `internal/codegen/{avro,ddl,connector}/`
- `cmd/dhctl` — subcomandos `contract validate|import`, `generate [--check]`
- `make generate`, `make verify`

## Como validar

```bash
make generate          # idempotente
git diff --exit-code   # segunda execução não muda nada
dhctl generate --check # 0
dhctl contract validate contracts/domains/**/*.yaml
# sabotagem: alterar um .avsc gerado à mão deve fazer `make verify` falhar
```
