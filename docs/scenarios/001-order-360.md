# Cenário 001 — Visão 360 do pedido

- **Perfil:** aplicacional
- **Pergunta de negócio:** "Me mostre tudo do pedido `ORD-000123`: itens, pagamentos, cliente, unidade de negócio e cupom, em uma única leitura."
- **Mecanismo:** Refreshable MV (`REFRESH EVERY 1 MINUTE APPEND`) para a tabela larga + `dictGet` para os cadastros pequenos (ADR-0005, árvore de decisão: correlação entre 2+ entidades mutáveis → Refreshable MV)
- **Frescor esperado:** ≤ 90 s entre o commit no SAP e a linha atualizada no mart (60 s de intervalo de refresh + duração do refresh + latência de ingestão L0→L1)
- **Janela de recálculo:** 3 dias (janela de *late arrival* padrão do ADR-0004 §7 / ADR-0005)
- **Entidades envolvidas:** `sales.order`, `sales.order_item`, `sales.order_payment`, `customer.customer`, `organization.business_unit` (dictionary), `pricing.discount_codes` (dictionary)
- **Tipo de correlação:** por ID (`order_id`, `customer_id`) + por coluna não-ID resolvida por dictionary (`business_unit_code`, `discount_code`)
- **ADRs relevantes:** ADR-0001 (L2), ADR-0004 (§4 leitura via `v_*_current`, §7 late arrival), ADR-0005 (§2 Refreshable MV, §3 Dictionary), ADR-0010 (checks), ADR-0011 (§1 `ORDER BY (order_id)`, §2 projection, §5 endpoint nomeado)

## Por que este cenário existe na PoC

Prova três coisas de uma vez:

1. **Que o ClickHouse consegue servir o caso aplicacional** — leitura por chave de
   uma linha desnormalizada de 6 entidades em dezenas de ms, sem um segundo store
   (a pergunta central do ADR-0011).
2. **Que a Refreshable MV se autocorrige.** É o cenário canônico do teste de
   *late arrival*: o `order_item` aterrissa antes do `order` (partições e
   connectors independentes, ADR-0004 §7). Uma MV incremental com `JOIN` gravaria
   `items_count = 0` **para sempre**; a Refreshable MV grava incompleto no
   primeiro refresh e **completo no seguinte**, sem intervenção.
3. **Que desnormalizar não exige abrir mão de corretude sobre dado mutável.** O
   pedido muda de status 5 vezes; o mart é recalculado por janela, não somado
   incrementalmente (ADR-0004 §6).

**Risco endereçado:** o antipadrão C do ADR-0005 ("tabela desnormalizada única
mantida por MV incremental com JOIN"). Este cenário entrega o mesmo resultado
desnormalizado pelo mecanismo correto, e o e2e prova a diferença.

## Fontes

| Tabela | Objeto lido | Camada | Por que este e não outro |
|---|---|---|---|
| Pedido | `dh_core.v_sales__order_current` | L1 | Estado atual deduplicado por `_cdc_seq` e sem linhas `_is_deleted=1`. Ler `dh_core.sales__order` direto retornaria N versões do mesmo pedido e pedidos apagados no SAP (ADR-0004 §4). |
| Itens | `dh_core.v_sales__order_item_current` | L1 | Mesma razão. Agregado por `order_id` **antes** do join, para não multiplicar linhas contra pagamentos. |
| Pagamentos | `dh_core.v_sales__order_payment_current` | L1 | Mesma razão. Agregado por `order_id` antes do join. |
| Cliente | `dh_core.v_customer__customer_current` | L1 | Cadastro **médio** e mutável: não cabe na regra de dictionary (< ~10M linhas *e* cadastro estável). `LEFT JOIN` dentro da Refreshable MV, que se autocorrige se o cliente chegar depois. |
| Unidade de negócio | `dh_core.dict__business_unit` | L2 | Poucos milhares de linhas, lookup por chave exata: dictionary tira o join do plano (`O(1)` em memória, ADR-0005 §3). |
| Cupom | `dh_core.dict__discount_codes` | L2 | Idem. O join é **por código string**, não por ID surrogate — ver cenário 004. |

Intenção declarada do `dictGet` (exigida pelo ADR-0005, consequências): aqui o
valor gravado é o **vigente no momento do refresh**, não o vigente no momento do
pedido. Para a tela de atendimento isso é o correto ("qual é o nome atual da BU
deste pedido"). Quem precisa do valor histórico usa o cenário 002/005.

## Modelo de saída

```sql
-- internal/contexts/analytics/sql/30-marts/0010__order_360.sql

CREATE TABLE IF NOT EXISTS dh_marts.order_360 {ON_CLUSTER}
(
    -- ---------- pedido (grão da tabela) ----------
    order_id                  String,
    customer_id               String,
    business_unit_code        LowCardinality(String),
    order_status              LowCardinality(String),
    channel                   LowCardinality(String),
    currency                  LowCardinality(String),
    discount_code             String,                 -- '' quando o pedido não usou cupom
    gross_amount              Decimal(18,4),
    discount_amount           Decimal(18,4),
    freight_amount            Decimal(18,4),
    total_amount              Decimal(18,4),
    order_created_at          DateTime64(3),
    order_updated_at          DateTime64(3),

    -- ---------- itens (agregado 1:N) ----------
    items_count               UInt32,                 -- linhas de item (item_seq distintos)
    items_distinct_item_ids   UInt32,
    items_quantity            Int64,
    items_gross_amount        Decimal(18,4),
    items_discount_amount     Decimal(18,4),
    items_total_amount        Decimal(18,4),
    items_dc_count            UInt32,                 -- centros de distribuição envolvidos
    items_first_item_id       String,                 -- item de menor item_seq (rótulo da tela)
    has_items                 UInt8,

    -- ---------- pagamentos (agregado 1:N) ----------
    payments_count            UInt32,
    payments_captured_count   UInt32,
    payments_denied_count     UInt32,
    payments_pending_count    UInt32,
    payment_methods           Array(String),
    authorized_amount         Decimal(18,4),
    captured_amount           Decimal(18,4),
    refunded_amount           Decimal(18,4),
    first_authorized_at       Nullable(DateTime64(3)),
    last_captured_at          Nullable(DateTime64(3)),
    is_fully_paid             UInt8,
    payment_gap_amount        Decimal(18,4),          -- total_amount - captured_amount (líquido de refund)

    -- ---------- cliente ----------
    customer_found            UInt8,
    customer_first_name       String,
    customer_segment          LowCardinality(String),
    customer_loyalty_tier     LowCardinality(String),
    customer_city             String,
    customer_state            LowCardinality(String),
    customer_since            Nullable(Date),

    -- ---------- unidade de negócio (dictionary) ----------
    bu_found                  UInt8,
    bu_name                   String,
    bu_channel                LowCardinality(String),
    bu_region                 LowCardinality(String),
    bu_active                 UInt8,

    -- ---------- cupom (dictionary) ----------
    discount_code_found       UInt8,
    discount_campaign_name    String,
    discount_type             LowCardinality(String),
    discount_value            Decimal(18,4),

    -- ---------- integridade ----------
    amount_mismatch_amount    Decimal(18,4),          -- total_amount - (items_total_amount + freight_amount)
    channel_mismatch          UInt8,                  -- order.channel != bu.channel

    -- ---------- controle do mart ----------
    _mart_version             UInt64,                 -- epoch ms do refresh; maior vence
    _refreshed_at             DateTime64(3)
)
ENGINE = ReplacingMergeTree(_mart_version)
PARTITION BY toYYYYMM(order_created_at)
ORDER BY (order_id);
```

**Justificativas do DDL**

- `ENGINE = ReplacingMergeTree(_mart_version)`: o refresh é `APPEND` por janela
  (não substituição total da tabela — o histórico fora da janela é estável, ADR-0005).
  Cada refresh reemite as mesmas `order_id` da janela; o `ReplacingMergeTree`
  colapsa pela maior `_mart_version`. Isso torna o refresh **idempotente** e faz
  a autocorreção funcionar: a versão completa, sendo mais nova, vence a incompleta.
- `ORDER BY (order_id)`: mandado pelo ADR-0011 §1 — a primeira coluna da chave de
  ordenação é aquela pela qual o acesso dominante filtra, e o acesso dominante
  aqui é `GET /orders/{order_id}/360`.
- `PARTITION BY toYYYYMM(order_created_at)`: `order_created_at` é **imutável**
  para um dado `order_id`. Isso não é detalhe estético — o `ReplacingMergeTree`
  deduplica **dentro da partição**. Se a chave de partição fosse derivada de
  `updated_at` ou de `_refreshed_at`, duas versões do mesmo pedido cairiam em
  partições diferentes e **nunca** colapsariam, deixando duplicata permanente.
- Sem `TTL`: mart aplicacional consultado por pedido antigo em atendimento.

Segunda chave de acesso (ADR-0011 §2), "pedidos deste cliente":

```sql
-- internal/contexts/analytics/sql/30-marts/0011__order_360_projection.sql
ALTER TABLE dh_marts.order_360 {ON_CLUSTER}
    ADD PROJECTION IF NOT EXISTS p_by_customer
    ( SELECT * ORDER BY (customer_id, order_created_at) );
```

Justificativa: `GET /customers/{customer_id}/orders` filtra por `customer_id`,
que não é prefixo do `ORDER BY`. É a 1ª das 2 projections permitidas sem novo ADR.
**Atenção:** consultas com `FINAL` não usam projection. Por isso o caminho por
cliente deduplica com `argMax(..., _mart_version)` em vez de `FINAL` — ver §Consumo.

## Transformação

```sql
-- internal/contexts/analytics/sql/30-marts/0012__mv_order_360.sql

CREATE MATERIALIZED VIEW IF NOT EXISTS dh_marts.mv__order_360 {ON_CLUSTER}
REFRESH EVERY 1 MINUTE APPEND
TO dh_marts.order_360
AS
WITH touched AS
(
    -- Conjunto de pedidos a recalcular. A janela é sobre `updated_at` de CADA
    -- uma das três origens, não só do pedido: é isso que faz a autocorreção de
    -- late arrival funcionar. Um item que chega hoje para um pedido criado há
    -- 5 dias reintroduz aquele order_id na janela.
    SELECT order_id FROM dh_core.v_sales__order_current
    WHERE updated_at >= now64(3) - INTERVAL 3 DAY
    UNION DISTINCT
    SELECT order_id FROM dh_core.v_sales__order_item_current
    WHERE updated_at >= now64(3) - INTERVAL 3 DAY
    UNION DISTINCT
    SELECT order_id FROM dh_core.v_sales__order_payment_current
    WHERE updated_at >= now64(3) - INTERVAL 3 DAY
)
SELECT
    o.order_id                                   AS order_id,
    o.customer_id                                AS customer_id,
    o.business_unit_code                         AS business_unit_code,
    o.order_status                               AS order_status,
    o.channel                                    AS channel,
    o.currency                                   AS currency,
    -- discount_code é Nullable na origem; o mart normaliza para '' e faz
    -- upper+trim porque o CDC do SAP entrega string com padding (ver cenário 004).
    upperUTF8(trimBoth(coalesce(o.discount_code, ''))) AS discount_code,
    o.gross_amount                               AS gross_amount,
    o.discount_amount                            AS discount_amount,
    o.freight_amount                             AS freight_amount,
    o.total_amount                               AS total_amount,
    o.created_at                                 AS order_created_at,
    o.updated_at                                 AS order_updated_at,

    i.items_count                                AS items_count,
    i.items_distinct_item_ids                    AS items_distinct_item_ids,
    i.items_quantity                             AS items_quantity,
    i.items_gross_amount                         AS items_gross_amount,
    i.items_discount_amount                      AS items_discount_amount,
    i.items_total_amount                         AS items_total_amount,
    i.items_dc_count                             AS items_dc_count,
    i.items_first_item_id                        AS items_first_item_id,
    if(i.items_count > 0, 1, 0)                  AS has_items,

    p.payments_count                             AS payments_count,
    p.payments_captured_count                    AS payments_captured_count,
    p.payments_denied_count                      AS payments_denied_count,
    p.payments_pending_count                     AS payments_pending_count,
    p.payment_methods                            AS payment_methods,
    p.authorized_amount                          AS authorized_amount,
    p.captured_amount                            AS captured_amount,
    p.refunded_amount                            AS refunded_amount,
    p.first_authorized_at                        AS first_authorized_at,
    p.last_captured_at                           AS last_captured_at,
    if(p.captured_amount - p.refunded_amount >= o.total_amount, 1, 0) AS is_fully_paid,
    toDecimal64(o.total_amount - (p.captured_amount - p.refunded_amount), 4) AS payment_gap_amount,

    c.customer_found                             AS customer_found,
    c.first_name                                 AS customer_first_name,
    c.segment                                    AS customer_segment,
    c.loyalty_tier                               AS customer_loyalty_tier,
    c.city                                       AS customer_city,
    c.state                                      AS customer_state,
    -- LEFT JOIN sem match devolve o DEFAULT do tipo (1970-01-01), não NULL.
    -- O flag customer_found é a única forma confiável de distinguir os dois.
    if(c.customer_found = 1, toNullable(c.customer_since), NULL) AS customer_since,

    dictHas('dh_core.dict__business_unit', tuple(o.business_unit_code)) AS bu_found,
    dictGetOrDefault('dh_core.dict__business_unit', 'bu_name',  tuple(o.business_unit_code), '') AS bu_name,
    dictGetOrDefault('dh_core.dict__business_unit', 'channel',  tuple(o.business_unit_code), '') AS bu_channel,
    dictGetOrDefault('dh_core.dict__business_unit', 'region',   tuple(o.business_unit_code), '') AS bu_region,
    dictGetOrDefault('dh_core.dict__business_unit', 'active',   tuple(o.business_unit_code), toUInt8(0)) AS bu_active,

    dictHas('dh_core.dict__discount_codes', tuple(upperUTF8(trimBoth(coalesce(o.discount_code, ''))))) AS discount_code_found,
    dictGetOrDefault('dh_core.dict__discount_codes', 'campaign_name', tuple(upperUTF8(trimBoth(coalesce(o.discount_code, '')))), '') AS discount_campaign_name,
    dictGetOrDefault('dh_core.dict__discount_codes', 'discount_type', tuple(upperUTF8(trimBoth(coalesce(o.discount_code, '')))), '') AS discount_type,
    dictGetOrDefault('dh_core.dict__discount_codes', 'discount_value', tuple(upperUTF8(trimBoth(coalesce(o.discount_code, '')))), toDecimal64(0, 4)) AS discount_value,

    toDecimal64(o.total_amount - (i.items_total_amount + o.freight_amount), 4) AS amount_mismatch_amount,
    if(dictHas('dh_core.dict__business_unit', tuple(o.business_unit_code))
       AND o.channel != dictGet('dh_core.dict__business_unit', 'channel', tuple(o.business_unit_code)), 1, 0) AS channel_mismatch,

    toUnixTimestamp64Milli(now64(3))             AS _mart_version,
    now64(3)                                     AS _refreshed_at
FROM
(
    SELECT *
    FROM dh_core.v_sales__order_current
    WHERE order_id IN (SELECT order_id FROM touched)
) AS o
LEFT JOIN
(
    -- Itens agregados ANTES do join. Se itens e pagamentos fossem unidos crus no
    -- mesmo nível, o produto cartesiano multiplicaria os valores dos dois lados
    -- (3 itens x 2 pagamentos = 6 linhas e todo sum() inflado 2x/3x).
    SELECT
        order_id,
        toUInt32(count())                              AS items_count,
        toUInt32(uniqExact(item_id))                   AS items_distinct_item_ids,
        toInt64(sum(quantity))                         AS items_quantity,
        toDecimal64(sum(gross_amount), 4)              AS items_gross_amount,
        toDecimal64(sum(discount_amount), 4)           AS items_discount_amount,
        toDecimal64(sum(total_amount), 4)              AS items_total_amount,
        toUInt32(uniqExactIf(dc_id, dc_id IS NOT NULL)) AS items_dc_count,
        argMin(item_id, item_seq)                      AS items_first_item_id
    FROM dh_core.v_sales__order_item_current
    WHERE order_id IN (SELECT order_id FROM touched)
    GROUP BY order_id
) AS i USING (order_id)
LEFT JOIN
(
    SELECT
        order_id,
        toUInt32(count())                                     AS payments_count,
        toUInt32(countIf(payment_status IN ('captured', 'refunded'))) AS payments_captured_count,
        toUInt32(countIf(payment_status = 'denied'))           AS payments_denied_count,
        toUInt32(countIf(payment_status = 'pending'))          AS payments_pending_count,
        arraySort(groupUniqArray(toString(payment_method)))    AS payment_methods,
        toDecimal64(sumIf(amount, payment_status IN ('authorized', 'captured', 'refunded')), 4) AS authorized_amount,
        toDecimal64(sumIf(amount, payment_status IN ('captured', 'refunded')), 4) AS captured_amount,
        toDecimal64(sumIf(amount, payment_status = 'refunded'), 4) AS refunded_amount,
        min(authorized_at)                                     AS first_authorized_at,
        max(captured_at)                                       AS last_captured_at
    FROM dh_core.v_sales__order_payment_current
    WHERE order_id IN (SELECT order_id FROM touched)
    GROUP BY order_id
) AS p USING (order_id)
LEFT JOIN
(
    -- `1 AS customer_found` é um marcador literal: é a forma robusta (e
    -- independente de join_use_nulls) de saber que o lado direito casou.
    SELECT customer_id, first_name, segment, loyalty_tier, city, state, customer_since,
           1 AS customer_found
    FROM dh_core.v_customer__customer_current
) AS c ON c.customer_id = o.customer_id
SETTINGS
    max_execution_time = 240,          -- refresh é pipeline, não request: teto próprio
    join_use_nulls = 0;                -- explícito: o contrato do mart usa flags *_found
```

## Regras de negócio

1. **Grão:** exatamente 1 linha por `order_id`. Pedido sem item e sem pagamento
   **aparece** (com `has_items = 0`), porque a tela de atendimento precisa mostrar
   o pedido recém-criado.
2. **Pedido apagado no SAP não aparece.** Garantido pela leitura de
   `v_sales__order_current` (ADR-0004 §5). Se o pedido for apagado depois de já
   estar no mart, a linha do mart **permanece** até o próximo refresh que a
   inclua na janela; fora da janela, exige `make mart-refresh` (ver Armadilhas).
3. **Item/pagamento apagado no SAP sai do agregado** no refresh seguinte, pelo
   mesmo mecanismo.
4. **Pedido cancelado aparece** com `order_status = 'canceled'` e valores
   preservados. O mart aplicacional não zera valores de pedido cancelado — quem
   decide excluir cancelado é o consumidor analítico (cenário 002). Filtrar aqui
   esconderia o pedido do atendimento, que é exatamente quem mais precisa vê-lo.
5. **`discount_code` ausente = `''`**, tanto para `NULL` quanto para string
   vazia/só espaços. Normalização obrigatória: `upperUTF8(trimBoth(...))`.
6. **Cupom não encontrado no cadastro** → `discount_code_found = 0`, com
   `discount_campaign_name = ''`. Não é erro de pipeline, é achado de qualidade
   (cenário 004). Nunca descartar o pedido.
7. **Cliente não encontrado** → `customer_found = 0`, `customer_since = NULL`,
   demais campos string `''`. Nunca descartar o pedido (ADR-0004 §7: órfão
   transitório é o funcionamento esperado).
8. **`authorized_amount` é cumulativo do funil:** conta `authorized`, `captured`
   e `refunded`, porque quem foi capturado necessariamente foi autorizado. Mesma
   lógica em `captured_amount` (inclui `refunded`). `payment_status = 'denied'` e
   `'pending'` não somam valor autorizado.
9. **`is_fully_paid`** compara `captured_amount - refunded_amount` com
   `total_amount`. Reembolso parcial derruba o flag — é o comportamento desejado.
10. **`payment_gap_amount` pode ser negativo** (sobrepagamento/ajuste do SAP).
    Não é clampado em zero: um gap negativo é informação, e clampar esconderia
    erro de conciliação.
11. **Moeda:** a linha carrega `currency` do pedido e **nenhum valor deste mart é
    somado entre pedidos**, portanto não há risco de soma entre moedas aqui. Os
    marts que somam (002, 004, 005) têm `currency` na chave.
12. **Valores monetários são `Decimal(18,4)`**, nunca `Float`. Somas
    intermediárias em `Decimal(38,4)` são convertidas de volta com
    `toDecimal64(..., 4)` explícito, para que overflow falhe em vez de truncar
    silenciosamente.
13. **`amount_mismatch_amount` não é corrigido**, só exposto. Divergência entre
    `order.total_amount` e `Σ itens + frete` significa (a) item ainda não chegou,
    (b) `discount_amount` aplicado em nível de cabeçalho, ou (c) erro de origem.
    Tolerância operacional: `abs() <= 0.01`.

## Armadilhas

- **(CLAUDE.md §8.1 — MV incremental não é join de streams.)** A tentação óbvia
  aqui é `CREATE MATERIALIZED VIEW ... TO order_360 AS SELECT ... FROM order JOIN
  order_item`. Não funciona: a MV só dispara em insert de `order`, então item que
  chega depois nunca entra; e o `JOIN` é resolvido no instante do insert, quando
  o outro lado pode estar vazio. O número sai errado e **não é corrigido**.
  `scripts/checks/no-join-in-incremental-mv.sh` bloqueia isso.
- **(CLAUDE.md §8.2/8.3 — `ReplacingMergeTree` é assíncrono.)** Ler
  `SELECT * FROM dh_marts.order_360 WHERE order_id = ?` **sem `FINAL`** devolve a
  versão de cada refresh que ainda não mergeou — a aplicação veria o pedido
  incompleto de um refresh anterior. Todo consumo passa por `FINAL` ou por
  `argMax(..., _mart_version)`.
- **Fan-out cartesiano.** Unir `order_item` e `order_payment` crus no mesmo nível
  multiplica linhas e infla todo `sum()`. Os dois lados são **pré-agregados por
  `order_id`** antes do `LEFT JOIN`. É o erro mais comum e o mais difícil de ver,
  porque o resultado continua "parecendo" plausível.
- **Chave de partição mutável quebra o dedup.** Ver justificativa do `PARTITION BY`.
- **`LEFT JOIN` sem match devolve default, não `NULL`** (`join_use_nulls = 0`).
  `bu_name = ''` e `customer_since = 1970-01-01` são *valores*, não ausência.
  Sem os flags `*_found`, "cliente não chegou" fica indistinguível de "cliente com
  nome vazio" — e uma média sobre `customer_since` traria 1970 para dentro.
- **CTE no ClickHouse é inlining, não materialização.** `touched` é referenciada
  4 vezes e portanto **executada 4 vezes**. Com janela de 3 dias e volume de PoC é
  aceitável; se `duration_ms` do refresh passar de 50% do intervalo
  (`system.view_refreshes`), a mitigação é materializar a janela em
  `dh_marts.order_360_window_keys` antes do refresh.
- **Amplificação de escrita do refresh por janela.** `REFRESH EVERY 1 MINUTE` com
  janela de 3 dias reemite os pedidos de 3 dias a cada minuto (≈ 4.320 reescritas
  da janela por dia). É o preço da autocorreção e deve ser **medido** em
  `docs/evaluation/`. Mitigação, se o custo aparecer: dividir em duas Refreshable
  MVs `APPEND` para a **mesma** tabela — uma quente (`EVERY 1 MINUTE`, janela 2 h)
  e uma fria (`EVERY 30 MINUTE`, janela 3 dias). O `_mart_version` torna a
  sobreposição segura.
- **Correção retroativa fora da janela não é vista** (ADR-0005). Um pedido de 40
  dias atrás que muda de status hoje só entra se `updated_at` estiver na janela —
  o que normalmente estará, já que `updated_at` é do SAP. Mas se o **atraso de
  ingestão** exceder a janela, `updated_at` já estará velho na chegada e o pedido
  nunca entra. Por isso `dq.rel.orphan_age_p99 < janela` é `error` e não `warn`.
- **`dictGet` grava valor *point-in-time* do refresh.** `bu_name` é o de agora,
  não o do dia do pedido. Declarado intencional em §Fontes; usar este mart para
  histórico de BU é erro de interpretação.
- **Dictionary com `COMPLEX_KEY_HASHED` exige `tuple(chave)`.** `dictGet(..., 'x',
  o.business_unit_code)` falha; o correto é `tuple(o.business_unit_code)`.

## Critérios de aceite

```sql
-- 1) Grão: uma linha por pedido
SELECT count() FROM (
  SELECT order_id, count() c FROM dh_marts.order_360 FINAL
  GROUP BY order_id HAVING c > 1
);
-- esperado: 0
```

```sql
-- 2) Cobertura: todo pedido da janela está no mart
SELECT count() FROM dh_core.v_sales__order_current o
LEFT JOIN (SELECT order_id FROM dh_marts.order_360 FINAL) m USING (order_id)
WHERE o.updated_at >= now64(3) - INTERVAL 3 DAY AND m.order_id = '';
-- esperado: 0
```

```sql
-- 3) Paridade de soma contra o core (dq.marts.sum_parity)
SELECT abs(
    (SELECT sum(total_amount) FROM dh_marts.order_360 FINAL
      WHERE order_created_at >= now64(3) - INTERVAL 3 DAY)
  - (SELECT sum(total_amount) FROM dh_core.v_sales__order_current
      WHERE created_at >= now64(3) - INTERVAL 3 DAY)
) <= 0.01 AS ok;
-- esperado: ok = 1
```

## Consumo

Endpoint (ADR-0011 §5 — contrato nomeado, nunca SQL do cliente):

```
GET /orders/{order_id}/360
  200 -> objeto único com os blocos order / items / payments / customer / bu / discount
  404 -> order_id inexistente no mart
  Frescor declarado no header: X-Data-Freshness-Seconds (intervalo de refresh + idade)
```

Query versionada em `internal/contexts/analytics/reports/order_360.sql`:

```sql
SELECT *
FROM dh_marts.order_360 FINAL

```

L3 como contrato de leitura estável (ADR-0001 §6 — sem lógica de negócio nova):

```sql
-- internal/contexts/analytics/sql/40-reports/0010__v_order_360.sql
CREATE VIEW IF NOT EXISTS dh_reports.v_order_360 {ON_CLUSTER} AS
SELECT * FROM dh_marts.order_360 FINAL;

-- Caminho por cliente: usa a PROJECTION p_by_customer, então NÃO pode usar FINAL
-- (consulta com FINAL não aproveita projection). Dedup por argMax.
CREATE VIEW IF NOT EXISTS dh_reports.v_customer_orders {ON_CLUSTER} AS
SELECT
    customer_id,
    order_id,
    argMax(order_status,     _mart_version) AS order_status,
    argMax(total_amount,     _mart_version) AS total_amount,
    argMax(currency,         _mart_version) AS currency,
    argMax(order_created_at, _mart_version) AS order_created_at,
    argMax(is_fully_paid,    _mart_version) AS is_fully_paid
FROM dh_marts.order_360
GROUP BY customer_id, order_id;
```

```
GET /customers/{customer_id}/orders?limit=50
-> SELECT * FROM dh_reports.v_customer_orders
   WHERE customer_id = {customer_id:String}
   ORDER BY order_created_at DESC LIMIT {limit:UInt32};
```
