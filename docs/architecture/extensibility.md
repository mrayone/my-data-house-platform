# Extensibilidade — como plugar o tópico 31

Este é o documento que prova o requisito central do projeto. Detalhamento do
[ADR-0003](../adr/0003-extensibilidade-contract-first.md).

## A promessa

Plugar um tópico novo custa:

- **1 arquivo YAML** escrito à mão
- **1 arquivo SQL** de camada core escrito à mão (a partir de esqueleto gerado)
- **0 linhas de Go**
- **0 arquivos existentes alterados**

Tudo o mais é gerado ou descoberto.

## O que é gerado a partir de quê

```
contracts/domains/<ctx>/<entidade>.yaml          ← ÚNICA fonte editada à mão
                    │
                    │  dhctl generate
                    ▼
   ┌────────────────┼────────────────┬──────────────────┬──────────────────┐
   ▼                ▼                ▼                  ▼                  ▼
schemas/avro/    internal/contexts/  deploy/connect/  deploy/kafka/   internal/contexts/
 <ctx>/           <ctx>/sql/          connectors/      topics.yaml      <ctx>/sql/
 <e>-value.avsc   10-landing/         <topic>.json     (entrada)        20-core/
 <e>-key.avsc     <seq>__<e>_raw.sql                                    <seq>__<e>.sql.tmpl
   │                  │                   │                │                  │
 GERADO            GERADO              GERADO           GERADO           ESQUELETO
 não editar        não editar          não editar       não editar       editar e renomear
```

Todo arquivo gerado carrega:
```
-- GENERATED by dhctl from contracts/domains/sales/order.yaml — DO NOT EDIT
-- contract-hash: 8f3a91c2b04e
```

`make verify` roda `dhctl generate --check`, que **falha se algum arquivo gerado
divergir do contrato**. Inconsistência entre schema Avro, DDL de landing e config
de connector deixa de ser possível: é erro de build.

## Passo a passo (o procedimento completo está em [`../runbooks/add-new-topic.md`](../runbooks/add-new-topic.md))

```bash
# 1. Descrever a entidade
$EDITOR contracts/domains/inventory/stock_movement.yaml

# 2. Validar o contrato
dhctl contract validate contracts/domains/inventory/stock_movement.yaml

# 3. Gerar os artefatos
make generate

# 4. Completar a camada core a partir do esqueleto
mv internal/contexts/inventory/sql/20-core/0030__stock_movement.sql.tmpl \
   internal/contexts/inventory/sql/20-core/0030__stock_movement.sql
$EDITOR internal/contexts/inventory/sql/20-core/0030__stock_movement.sql

# 5. Aplicar
make bootstrap      # tópico + schema + migrations + connector, na ordem

# 6. Verificar
dhctl dq run --severity error
```

Se a entidade precisa aparecer num relatório, isso é um **cenário novo** com doc
próprio em [`../scenarios/`](../scenarios/) — e é a única parte que exige decisão
humana de modelagem, por desenho ([ADR-0005](../adr/0005-estrategia-de-agregacao-mv-refreshable-dictionary.md)).

## Anatomia do contrato

```yaml
apiVersion: datahouse/v1
kind: EntityContract

metadata:
  context: inventory              # define a pasta em 3 lugares (contracts/schemas/internal)
  entity: stock_movement
  owner: time-logistica
  description: Movimentações de estoque replicadas do SAP via Datasphere

source:
  system: sap
  cdc: datasphere
  envelope: flat                  # flat | debezium
  topic: sap.inventory.stock_movement.v1
  partitions: 6
  key: [movement_id]              # chave Kafka e chave de negócio
  version_column: cdc_seq         # AUTORIDADE de ordem (ADR-0004)
  operation_column: op            # c | u | d | r
  soft_delete_operations: [d]
  freshness_sla_minutes: 15       # alimenta dq.landing.freshness

schema:
  fields:
    - { name: movement_id,  type: string,            nullable: false, doc: PK da movimentação }
    - { name: item_id,      type: string,            nullable: false, doc: SKU }
    - { name: dc_id,        type: string,            nullable: false, doc: Centro de distribuição }
    - { name: movement_type,type: string,            nullable: false, doc: in | out | transfer | adjust }
    - { name: quantity,     type: int64,             nullable: false }
    - { name: unit_cost,    type: decimal, precision: 18, scale: 4 }
    - { name: moved_at,     type: timestamp_micros,  nullable: false }
    - { name: created_at,   type: timestamp_micros,  nullable: false }
    - { name: updated_at,   type: timestamp_micros,  nullable: false }

landing:
  partition_by: toYYYYMM(_kafka_ts)
  order_by: [movement_id, _cdc_seq]      # com _cdc_seq: L0 guarda todas as versões
  ttl_days: 180                           # >= retenção do Kafka; mínimo 90

core:
  engine: ReplacingMergeTree
  order_by: [movement_id]                 # SEM _cdc_seq: senão nada deduplica
  partition_by: toYYYYMM(moved_at)

relations:
  - to: inventory/stock_position
    kind: lookup
    join_on: { local: [item_id, dc_id], remote: [item_id, dc_id] }
  - to: pricing/prices
    kind: lookup
    join_on: { local: item_id, remote: item_id }

extensions:
  serving: false        # exposto pela API?
  analytics: true       # participa de marts?
```

### `relations` é documentação executável

Não gera JOIN. Serve para três coisas concretas:

1. **Desenhar o mapa** de [`data-flow.md`](data-flow.md) — que assim não apodrece.
2. **Validar** que a relação declarada aponta para um contrato existente
   (`dhctl contract validate` falha se `to:` não existir).
3. **Gerar os checks** `dq.rel.fk_violation` e `dq.rel.orphan_rate`
   ([ADR-0010](../adr/0010-observabilidade-e-qualidade-de-dados.md)).

*Como* correlacionar continua sendo decisão humana, registrada no doc do cenário.
O contrato declara que a relação **existe**; o cenário decide o que fazer com ela.

## Mapeamento de tipos (normativo)

| Contrato | Avro | ClickHouse (L0 e L1) |
|---|---|---|
| `string` | `string` | `String` |
| `string` + `low_cardinality: true` | `string` | `LowCardinality(String)` |
| `bool` | `boolean` | `UInt8` |
| `int32` | `int` | `Int32` |
| `int64` | `long` | `Int64` |
| `float64` | `double` | `Float64` — **proibido para dinheiro** |
| `decimal(p,s)` | `bytes` + `logicalType: decimal` | `Decimal(p,s)` |
| `date` | `int` + `logicalType: date` | `Date32` |
| `timestamp_millis` | `long` + `logicalType: timestamp-millis` | `DateTime64(3)` |
| `timestamp_micros` | `long` + `logicalType: timestamp-micros` | `DateTime64(6)` |
| `bytes` | `bytes` | `String` |
| `array<T>` | `array` | `Array(T)` |
| `map<string,T>` | `map` | `Map(String, T)` |
| `enum` (+ `values`) | `enum` | `Enum8`/`Enum16` |
| qualquer `nullable: true` | `["null", T]` com `default: null` | `Nullable(T)` |

Regras que o gerador aplica sozinho:
- `nullable: true` **exige** `default: null` no Avro — sem isso a compatibilidade
  `BACKWARD` quebra ([ADR-0006](../adr/0006-convencoes-avro-e-schema-registry.md)).
- Colunas técnicas `_topic`, `_partition`, `_offset`, `_kafka_ts`,
  `_ingested_at`, `_op`, `_cdc_seq`, `_schema_id` são injetadas em toda tabela L0.
- `_cdc_seq` e `_is_deleted` são injetadas em toda tabela L1.

**Tipo fora desta tabela não é improvisado no YAML.** A validação falha com
mensagem apontando o tipo; adicionar tipo novo é alterar
`internal/codegen/` e esta tabela, no mesmo commit.

## Adicionar um contexto novo

```bash
mkdir -p contracts/domains/logistics
mkdir -p schemas/avro/logistics
mkdir -p internal/contexts/logistics/{generator,reports}
mkdir -p internal/contexts/logistics/sql/{10-landing,20-core,30-marts,40-reports}
$EDITOR internal/contexts/logistics/CLAUDE.md      # obrigatório
```

Nada a registrar em arquivo central. O runner de migrations e o gerador
descobrem por glob, e a ordenação é derivada do número da camada
([ADR-0007](../adr/0007-migrations-sql-versionado.md),
[ADR-0009](../adr/0009-layout-de-pastas-context-first.md)).
**Zero conflito de merge** entre branches que adicionam contextos diferentes.

## Fronteiras de dependência (enforçadas)

```
cmd/*  ──>  internal/contexts/*  ──>  internal/platform/*
                    │
                    └──X──>  internal/contexts/<outro>     PROIBIDO
```

| Regra | Check |
|---|---|
| `contexts/a` não importa `contexts/b` | `scripts/checks/context-boundaries.sh` |
| `platform` não importa `contexts` | `scripts/checks/context-boundaries.sh` |
| SQL de um contexto só referencia objetos daquele contexto (+ dictionaries) | `scripts/checks/no-cross-context-sql.sh` |

Cruzou contexto? Vai para o contexto `analytics`, que é exatamente o lugar dos
marts cross-context.

## Custo marginal medido

Meta a ser verificada na Fase 07, adicionando uma 9ª entidade de teste
(`inventory/stock_movement`) e cronometrando:

| Item | Meta |
|---|---|
| Arquivos escritos à mão | 2 (contrato + SQL core) |
| Arquivos existentes alterados | 0 |
| Linhas de Go escritas | 0 |
| Comandos até dado agregado | 3 (`make generate`, `make bootstrap`, `dhctl dq run`) |
| Tempo de ponta a ponta | < 30 min |

Se qualquer item estourar, **o gerador está incompleto** — e isso é um achado da
PoC, não um detalhe: é a diferença entre uma plataforma e um conjunto de scripts.
