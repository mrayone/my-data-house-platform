# Runbook — plugar um tópico novo

Este é o procedimento que **prova o requisito central do projeto**: plugar o tópico
31 custa configuração, não código.

- Promessa e mecânica: [`../architecture/extensibility.md`](../architecture/extensibility.md)
- Decisão: [ADR-0003](../adr/0003-extensibilidade-contract-first.md)
- Medição do custo real: [`../evaluation/extensibility-drill.md`](../evaluation/extensibility-drill.md)

**Custo esperado:** 2 arquivos escritos à mão, 0 linhas de Go, 0 arquivos
existentes alterados.

---

## Procedimento

### 1. Escreva o contrato

```bash
$EDITOR contracts/domains/<contexto>/<entidade>.yaml
```

Se a entidade já existe no Schema Registry (cenário real), comece pelo import e
complete as decisões de plataforma:

```bash
./bin/dhctl contract import \
  --from-subject sap.<contexto>.<entidade>.v1-value \
  --context <contexto> --entity <entidade> \
  > contracts/domains/<contexto>/<entidade>.yaml
```

O import traz os campos e os tipos. **As decisões de plataforma são suas** — o
schema do SAP não as contém. Ver §"Decisões que você tem de tomar".

### 2. Valide

```bash
./bin/dhctl contract validate contracts/domains/<contexto>/<entidade>.yaml
```

A validação reporta **todos** os problemas de uma vez. Corrija e repita até sair 0.

### 3. Gere os artefatos

```bash
make generate
git diff        # revise o que foi gerado antes de prosseguir
```

Isso produz, sem intervenção:

| Artefato | Caminho |
|---|---|
| Schema Avro do valor | `schemas/avro/<ctx>/<entidade>-value.avsc` |
| Schema Avro da chave | `schemas/avro/<ctx>/<entidade>-key.avsc` |
| DDL da tabela de landing | `internal/contexts/<ctx>/sql/10-landing/<seq>__<entidade>_raw.sql` |
| Config do connector | `deploy/connect/connectors/sap.<ctx>.<entidade>.v1.json` |
| Entrada do tópico | `deploy/kafka/topics.yaml` |
| **Esqueleto** da camada core | `internal/contexts/<ctx>/sql/20-core/<seq>__<entidade>.sql.tmpl` |

**Nenhum desses arquivos é editado à mão**, exceto o esqueleto. Todos carregam o
header `GENERATED by dhctl` e um `contract-hash`; `make verify` falha se algum
divergir do contrato.

### 4. Complete a camada core

```bash
mv internal/contexts/<ctx>/sql/20-core/<seq>__<entidade>.sql.tmpl \
   internal/contexts/<ctx>/sql/20-core/<seq>__<entidade>.sql
$EDITOR internal/contexts/<ctx>/sql/20-core/<seq>__<entidade>.sql
```

O esqueleto já traz os três objetos obrigatórios; remova a linha `SKELETON`,
resolva os `-- TODO:` e confira:

1. **Tabela** `dh_core.<ctx>__<entidade>` com
   `ReplacingMergeTree(_cdc_seq, _is_deleted)` e `ORDER BY` = chave de negócio.
2. **MV incremental** L0→L1, **sem `JOIN`**, aplicando
   `if(_op = 'd', 1, 0) AS _is_deleted`.
3. **View corrente** `dh_core.v_<ctx>__<entidade>_current` com `FINAL` **e**
   `WHERE _is_deleted = 0`.

### 5. Aplique

```bash
make bootstrap    # topics -> schemas -> migrate -> connectors -> status
```

A ordem importa, e o porquê está em [`bootstrap.md`](bootstrap.md).

### 6. Verifique

```bash
make connectors-status
./bin/dhctl dq run --severity error
make verify
```

E confirme que o dado chegou:

```sql
SELECT count(), max(_kafka_ts) FROM dh_landing.<ctx>__<entidade>_raw;
SELECT count() FROM dh_core.v_<ctx>__<entidade>_current;

-- nenhuma chave duplicada
SELECT count() FROM (
  SELECT <chave>, count() c FROM dh_core.v_<ctx>__<entidade>_current
  GROUP BY <chave> HAVING c > 1
);   -- esperado: 0
```

### 7. Se a entidade precisa aparecer num relatório

Isso é um **cenário novo**, não parte deste runbook. É a única etapa que exige
decisão humana de modelagem, por desenho
([ADR-0005](../adr/0005-estrategia-de-agregacao-mv-refreshable-dictionary.md)):
siga [`../scenarios/README.md`](../scenarios/README.md) → "Como adicionar um
cenário novo".

## Decisões que você tem de tomar

O schema do SAP não contém nenhuma destas. São as decisões de plataforma, e são a
razão de o contrato existir em vez de derivarmos tudo do Schema Registry.

| Campo | A pergunta | Como decidir |
|---|---|---|
| `source.key` | qual é a chave de negócio? | a PK da tabela de origem; compõe a chave Kafka e o `ORDER BY` de L1 |
| `source.version_column` | qual coluna diz qual versão é mais nova? | LSN / sequência de commit do CDC. **Monotônica por chave.** Sem ela, evento fora de ordem sobrescreve estado novo com velho |
| `source.operation_column` | onde vem `c`/`u`/`d`/`r`? | coluna de operação do Datasphere |
| `source.freshness_sla_minutes` | quanto tempo sem mensagem é normal? | transacional ~10 min; cadastro pode ser 24 h. Alimenta `dq.landing.freshness` |
| `source.partitions` | quantas partições? | pela taxa esperada. **Não pode ser reduzido depois** |
| `landing.order_by` | como L0 organiza as versões? | `[<chave...>, _cdc_seq]` — **termina em `_cdc_seq`** |
| `landing.ttl_days` | por quanto tempo o reprocesso é possível? | ≥ retenção do Kafka. Mínimo 90 |
| `core.order_by` | como L1 deduplica? | a chave de negócio, **sem `_cdc_seq`** |
| `core.partition_by` | como particionar o estado atual? | uma coluna de data estável (data de criação, não de atualização) |
| `core.expose_as_dictionary` | é cadastro pequeno consultado por chave? | até ~10M linhas e estável ⇒ sim |
| `relations` | com o que se conecta, e de que tipo? | `foreign_key` (deve existir) · `lookup` (pode faltar) · `temporal` (ASOF) · `loose` (só compartilha coluna). **O `kind` decide quais checks de qualidade são gerados** |
| `extensions.serving` / `analytics` | quem consome? | define se aparece na API e se participa de marts |
| `extensions.pii` | contém dado pessoal? | exige coluna hasheada e fica fora de log |

## Erros comuns

| Erro | Sintoma | Correção |
|---|---|---|
| `_cdc_seq` no `core.order_by` | **nada deduplica** — cada versão é uma linha | remova `_cdc_seq` do `core.order_by` |
| `_cdc_seq` ausente no `landing.order_by` | versões se sobrescrevem em L0; reprocesso perde histórico | acrescente `_cdc_seq` ao final |
| chave `on:` em vez de `join_on:` | a relação desaparece silenciosamente | em YAML 1.1, `on` é o booleano `true`. Use `join_on` |
| vírgula em `doc:` sem aspas dentro de `{ ... }` | erro de parse confuso, ou campo truncado | ponha o valor entre aspas |
| `ttl_days` abaixo de 90 | `contract-ttl.sh` falha | aumente; reprocesso depende disso |
| tipo fora da tabela de mapeamento | validação falha nomeando o tipo | use um tipo suportado, ou altere `internal/codegen/` e a tabela de `extensibility.md` no mesmo commit |
| `float64` para dinheiro | `dq.money.no_float` falha | use `decimal` com `precision` e `scale` |
| `nullable: true` sem `default: null` no Avro | compatibilidade `BACKWARD` quebra | o gerador faz isso sozinho; se não fez, é bug do gerador |
| `relations[].to` apontando para contrato inexistente | validação falha | crie o contrato do outro lado primeiro, ou corrija o caminho |
| editar o `.avsc` ou o DDL gerado | `make verify` falha com o arquivo divergente | corrija o **contrato** e rode `make generate` |
| esqueleto `.sql.tmpl` deixado sem renomear | a migration não é aplicada (o runner só lê `.sql`) | renomeie para `.sql` |
| `JOIN` na MV de L0→L1 | `no-join-in-incremental-mv.sh` falha | correlação não é papel de L1. Vai para um mart (ADR-0005) |

## Mudança incompatível de schema

`BACKWARD` proíbe remover campo e adicionar campo obrigatório
([ADR-0006](../adr/0006-convencoes-avro-e-schema-registry.md) §4). Quando a mudança
é incompatível, **não se edita o contrato existente**:

1. Crie `contracts/domains/<ctx>/<entidade>_v2.yaml` com
   `source.topic: sap.<ctx>.<entidade>.v2` — o `v<n>` é versão de **contrato**.
2. `make generate && make bootstrap` — o tópico, o schema, a tabela de landing e o
   connector novos passam a existir **ao lado** dos antigos.
3. Escreva a camada core do `v2`. Se as duas versões alimentam a mesma tabela core,
   adicione uma segunda MV incremental apontando para ela — é o caso legítimo de
   duas MVs com o mesmo destino.
4. Conviva com as duas versões pelo tempo necessário para a origem migrar.
5. Desative o connector antigo (`dhctl connectors pause` e depois `delete`), mas
   **mantenha a tabela de landing antiga** até o TTL expirar: ela é o histórico
   reprocessável.
6. Marque o contrato antigo com `metadata.tags: [deprecated]` e registre a data de
   remoção.

Antes de publicar, teste sem publicar:

```bash
./bin/dhctl schemas check-compat contracts/domains/<ctx>/<entidade>.yaml
```
