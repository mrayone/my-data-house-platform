## 1. O que é este projeto

PoC de uma **data platform de agregação sobre ClickHouse**, alimentada por
**N tópicos Kafka (Confluent) em Avro**, produzidos por **CDC do SAP via
Datasphere**.

**Objetivo de negócio da PoC:** produzir evidência técnica e de custo suficiente
para decidir a contratação do **ClickHouse Cloud no GCP**. Todo entregável deve
contribuir para essa decisão — ver `docs/evaluation/`.

**Dois consumidores dos dados, igualmente importantes:**

1. **Aplicações** (baixa latência, acesso por chave — ex.: "tudo do pedido X").
2. **Analítico** (agregações, relatórios, séries temporais).

**Requisito estrutural central:** plugar um novo tópico deve custar
**configuração + SQL declarativo**, nunca código Go novo. Ver
`docs/architecture/extensibility.md`.

## 2. Stack (fixa — não substituir sem ADR)

| Camada | Escolha |
|---|---|
| Armazenamento/compute | ClickHouse **self-hosted** (paridade com ClickHouse Cloud) |
| Coordenação | ClickHouse Keeper |
| Streaming | Kafka + Confluent Schema Registry (Avro) |
| Ingestão | **ClickHouse Kafka Connect Sink** (Kafka Connect) — ver `docs/adr/0002` |
| Linguagem | **Go** (CLI de plataforma, produtor de carga, API de relatórios) |
| Orquestração local | Docker Compose |
| Migrations | SQL versionado, executado por `dhctl migrate` |

**Go não faz ingestão linha-a-linha no caminho principal.** O papel do Go é:
`dhctl` (codegen + migrations + provisionamento), `producer` (gerador de carga
CDC em Avro) e `api` (serving dos relatórios). Ver `docs/adr/0002`.

## 4. Regras invioláveis

1. **Não altere um ADR aceito.** Se a decisão mudou, crie um ADR novo com
   status `Accepted` que declare `Supersedes: ADR-000X`, e marque o antigo como
   `Superseded by: ADR-000Y`.
2. **Nada de arquivo gerado editado à mão.** `schemas/avro/**`, configs em
   `deploy/connect/connectors/**` e DDL de landing são saída de `dhctl generate`.
   Todo arquivo gerado carrega o header `-- GENERATED by dhctl`. Para mudar a
   saída, mude o contrato ou o gerador.
3. **Nenhum tópico novo justifica código Go novo.** Se você acha que precisa,
   é sinal de que o modelo de contrato está incompleto — abra um ADR.
4. **SQL é declarativo e idempotente.** Toda migration usa
   `CREATE ... IF NOT EXISTS`. Nunca `DROP` sem uma migration explícita de
   reversão documentada.
5. **Sem segredo no repositório.** Somente `.env.example`.
6. **Cada tarefa da fase termina em commit.** Ver §5.
7. **Se um critério de aceite não passa, a tarefa não está concluída.** Registre
   o bloqueio em `docs/plan/PROGRESS.md` e pare — não invente workaround
   silencioso.
8. **Escreva a documentação em pt-BR.** Identificadores de código, SQL, nomes de
   tabela/coluna/tópico em inglês `snake_case`.

## 5. Protocolo de trabalho (obrigatório para agentes executores)

### 5.1 Antes de começar
1. Leia este `CLAUDE.md`.
2. Leia `docs/plan/PROGRESS.md` para saber o estado atual.
3. Leia `docs/plan/phases/phase-NN-*.md` da fase que vai executar.
4. Leia os ADRs listados em "ADRs relevantes" daquela fase.
5. Confirme que a fase anterior está marcada `DONE` em `PROGRESS.md`. Se não
   estiver, não comece — registre e pare.

### 5.2 Branch
Uma branch por fase:

```
git checkout main && git pull
git checkout -b feat/phase-NN-<slug>     # ex.: feat/phase-04-landing-ingestion
```

### 5.3 Um commit por tarefa
Cada tarefa da fase (`PNN-TX`) gera **um commit**, contendo: o código/SQL/config
da tarefa **+** a atualização de `docs/plan/PROGRESS.md` **+** qualquer doc que a
tarefa mande atualizar.

Formato da mensagem (Conventional Commits + ID da tarefa):

```
<tipo>(<escopo>): <resumo no imperativo>

Tarefa: P04-T02
Fase: 04 - Landing e ingestão
Critérios de aceite:
- [x] <critério 1 copiado da fase>
- [x] <critério 2>
Validado com: make <comando>
```

`tipo` ∈ `feat|fix|docs|refactor|test|chore|perf|build`.
`escopo` ∈ `platform|contracts|codegen|migrate|ingestion|sales|customer|organization|pricing|inventory|analytics|reporting|deploy|docs|plan`.

### 5.4 Registro de progresso
Em `docs/plan/PROGRESS.md`, ao concluir a tarefa, atualize a linha da tarefa com
status, data, hash curto do commit e uma observação de uma linha. Ao concluir a
fase, atualize também o bloco de resumo da fase.

### 5.5 Fim da fase
1. Todos os critérios de aceite da fase verificados.
2. `make verify` verde.
3. `PROGRESS.md` com a fase `DONE`.
4. Se a implementação divergiu de um ADR, ADR novo escrito antes do merge.
5. Abra a branch para revisão (não faça merge em `main` por conta própria).

## 6. Comandos

Sempre via `Makefile` — nunca comandos avulsos em documentação.

| Comando | Efeito |
|---|---|
| `make up` / `make down` | sobe/derruba o ambiente local |
| `make bootstrap` | tópicos + schemas + migrations + connectors, na ordem |
| `make generate` | roda `dhctl generate` (avsc, DDL de landing, configs de connector) |
| `make migrate` | aplica migrations no ClickHouse |
| `make seed` | produz carga CDC sintética nos tópicos |
| `make reports` | executa os relatórios dos cenários e imprime os resultados |
| `make verify` | lint + testes + checagem de arquivos gerados sujos + smoke e2e |
| `make bench` | benchmark para `docs/evaluation/` |

Regra: se um passo do runbook não tem alvo no `Makefile`, **crie o alvo** em vez
de documentar o comando cru.

## 7. Convenções de nomenclatura

| Objeto | Padrão | Exemplo |
|---|---|---|
| Tópico Kafka | `sap.<contexto>.<entidade>.v<n>` | `sap.sales.order.v1` |
| Subject do Schema Registry | `<topic>-value` / `<topic>-key` | `sap.sales.order.v1-value` |
| Database ClickHouse | `dh_landing`, `dh_core`, `dh_marts`, `dh_reports` | — |
| Tabela landing (L0) | `dh_landing.<contexto>__<entidade>_raw` | `dh_landing.sales__order_raw` |
| Tabela core (L1) | `dh_core.<contexto>__<entidade>` | `dh_core.sales__order` |
| Mart (L2) | `dh_marts.<assunto>` | `dh_marts.order_360` |
| Materialized view | `<db>.mv__<origem>__to__<destino>` | `dh_core.mv__sales__order_raw__to__order` |
| Dictionary | `dh_core.dict__<entidade>` | `dh_core.dict__business_unit` |
| Arquivo de migration | `<NN>-<camada>/<seq>__<descrição>.sql` | `20-core/0010__sales_order.sql` |
| Contrato | `contracts/domains/<contexto>/<entidade>.yaml` | `contracts/domains/sales/order.yaml` |

Colunas técnicas presentes em toda tabela L0 (prefixo `_`):
`_topic`, `_partition`, `_offset`, `_kafka_ts`, `_ingested_at`,
`_op` (`c`/`u`/`d`/`r`), `_cdc_seq`, `_schema_id`.

## 8. Armadilhas conhecidas do ClickHouse (leia antes de codar)

1. **Materialized View incremental é um trigger de INSERT, não um join de
   streams.** Ela só dispara na tabela de origem declarada no `FROM`, e só vê o
   bloco inserido. `JOIN` dentro de MV incremental lê a tabela da direita no
   instante do insert — se o outro lado ainda não chegou (CDC fora de ordem), o
   dado sai errado **e não é corrigido depois**. Correlação entre entidades usa
   **Refreshable MV** ou JOIN em tempo de query. Ver `docs/adr/0005`.
2. **`ReplacingMergeTree` deduplica de forma assíncrona e sem garantia de
   momento.** Leitura correta exige `FINAL` ou agregação por
   `argMax(col, _cdc_seq)`. Nunca assuma "já mergeou".
3. **`_is_deleted` do `ReplacingMergeTree` só é aplicado com `FINAL` ou
   `OPTIMIZE ... CLEANUP`.** Sem isso, linha deletada continua visível.
4. **Agregação sobre dado mutável quebra.** `SummingMergeTree`/
   `AggregatingMergeTree` são aditivos: se um UPDATE do CDC reescreve a mesma
   chave, você soma duas vezes. Agregado incremental só sobre fatos
   append-only; entidade mutável agrega via Refreshable MV. Ver `docs/adr/0004`.
5. **O Kafka Connect Sink é 1 tópico → 1 tabela, sem transformação e sem
   delete.** Isso é proposital: a ingestão é burra, o modelo mora no ClickHouse.
   Delete de CDC vira coluna, não `DELETE`. Ver `docs/adr/0002` e `0004`.
6. **Chave de ordenação é decisão de performance de leitura.** `ORDER BY` errado
   inviabiliza o acesso por chave que as aplicações precisam. Ver `docs/adr/0011`.

## 9. Contextos (bounded contexts)

| Contexto | Entidades | Dono do quê |
|---|---|---|
| `sales` | `order`, `order_item`, `order_payment` | fatos transacionais do pedido |
| `customer` | `customer` | dados de cliente |
| `organization` | `business_unit` | estrutura organizacional/canal |
| `pricing` | `prices`, `discount_codes` | preço de tabela e promoções |
| `inventory` | `stock_position` | posição de estoque por CD |
| `analytics` | — (sem tópico) | marts e relatórios que cruzam contextos |

Contexto novo = pasta nova em `contracts/domains/`, `schemas/avro/` e
`internal/contexts/`. Nada a renumerar, nada a registrar em lugar central.
